Design notes

  1. The seat line is the number delegators care about: the weight to beat for the last seat. It's derived from indexed boardSeat rows. A tie keeps the incumbent, so the "needs" figure is always margin + 1 (612,000 − 540,000 + 1 = 72,001).
  2. One ranked table replaces the decorative semicircle and the separate leaderboard in BoardVisualization.tsx. Each row shows the full authority chain (seat NFT → owner → session key), because that's what decides who can act. The rows come from boardSeat, membershipToken and directorOperator in chamber-indexer, with no getTop, ownerOf or getDirectorOperator calls (I-13, I-6).
  3. Weight is stored in cLORE shares, and people think in LORE. The column shows LORE at the current share price, with the cLORE amount in a tooltip. cLORE has 21 decimals (18 + _decimalsOffset 3): about 1,000 share units per LORE base unit, which is about 1 cLORE per LORE in display units. The old leaderboard formatted shares with 18 decimals (BoardVisualization.tsx:482), so weights read 1,000 times too large, with a vault symbol that looked like a different token. The delegate form parses amounts with the share decimals, as DelegationManager already does.
  4. Maturity comes from the contract's stored seatedAt, which is the seating block + SEATING_DELAY (1 block). A seat can act once the head reaches it, checked against the indexer head clock. An NFT transfer restarts the clock (syncSeatingControl, PMN-H01). "Seated since" shows the seating block and "Can act since" shows seatedAt. Today useDirectorActionGate polls useBlockNumber every 60 s for this (I-10, I-13).
  5. The session key column says why a key is missing (EOA owners can't set one), shows scope bits as chips, and warns about expiry before a key lapses. Stale keys (NFT transferred, key cleared) come from the indexer's staleness view (I-6). Copy says "session key"; "Operators" survives only as the top-nav label (P-8, P-9).
  6. Seat-count changes have their own card, not a line in the activity list. The lifecycle shows the 7-day timelock (SEAT_UPDATE_TIMELOCK) and the 14-day point (SEAT_UPDATE_EXPIRY) after which any director may delete it; before that only the proposer can. Support is a secondary button, not the primary one: supporting moves the board toward a change that would stall #46. The consequences are spelled out, including the effect on open proposals, because _requiredConfirmations = max(submit quorum, live quorum).
  7. Quorum math is shown with the reachable count and a lookup row, so a director can predict the effect of a seat change or a burned NFT. Reachability follows BoardLib.countReachableAuthorized (PMN-M01).
  8. The preview is computed locally from indexer rows and says so. The only RPC is at transaction time: useSimulateDelegate runs before signing, then the receipt. After the receipt, the freshness gate (requireIndexerBlock, keyed by chain and Chamber in I-10) holds the ranking until the indexer reaches that block, so the table never shows pre-write state. Simulate hooks move to src/lib/tx/, the only place the lint rule allows contract reads (I-11, I-13).
  9. The lock is stated where people delegate. Chamber._update reverts with ExceedsDelegatedAmount when a transfer would dip into delegated shares. Public copy that implied otherwise is being removed (D-6).
  10. Independence mirrors the seated-board precondition for the LORE handoff: a seated, mature board with quorum 3 or more and independent holders (review "Critical: the LORE handoff…", M-10, M-23). The card is honest about its limits. It checks owner addresses, not humans, and Safe signer overlap isn't indexed yet.
  11. A seat change or delegation that would give one owner quorum-many seats would flip this card red and add a warning to the seat-change card. That's the concentration the review's 1-of-N finding warns about.
  12. The AI seat is labelled as an agent director. Its owner is a policy Safe that checks each confirmation against the agent's mandate, and its session key deliberately lacks CONFIRM. Because a submit records the submitter's confirmation, a submit through that key still counts for seat #31, so the policy account should also vet what the key submits (C-17). ERC-8004 identity is display only; it isn't a security primitive (review "AI agents are directors, not relayers").
