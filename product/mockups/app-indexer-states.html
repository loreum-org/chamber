Indexer freshness states

Every number in the app comes from chamber-indexer. This sheet defines how the app knows whether that data is current, what the freshness chip says, and how pages behave when the indexer is healthy, lagging, or stalled or unreachable. In none of these states does the app fall back to reading the chain for display.

Why this exists 1

Incident · Sep 2026

On Sep 20, 2026 at 21:21 UTC the production indexer stopped advancing. For 6.5 days it kept answering queries and kept reporting ready: true, while it fell 46,768 blocks behind Sepolia (11,746,692 vs 11,793,460). The app had no freshness UI, so app.loreum.org's queue quietly hid proposals that had already executed. Nobody noticed.

The same month, display-time RPC polling (17 event watchers per Chamber page, a pending-transaction watcher and 4-second block polling) used up the entire Alchemy compute quota. Falling back to RPC when the indexer misbehaves isn't an option.

Rules
  1. Freshness is the age of the last indexed block, measured against the clock. The ready flag is ignored.
  2. When data is old, show it with its age. Never blank a page that has data, and never refill it from RPC.
  3. Pause writes whose decision depends on current state. Keep protective actions available. Transaction-time simulation still runs via RPC.

After the receipt, reads for this Chamber require an indexer head at or past the receipt's block. The gate is keyed by chain and Chamber (1:0x3f1c…a92e), so a write on one chain never blocks another. Cards touched by the write keep their old values, marked "updating", instead of flashing pre-write state.

Design notes

  1. The Sep 2026 stall is the reason for this sheet. The indexer reported ready: true while it was 46,768 blocks (6.5 days) behind, and the app trusted it (I-1). The same month, display-time RPC polling burned the Alchemy quota, so "fall back to RPC" is ruled out by the standing rule that display reads come only from chamber-indexer (D-9 ADR-0002). This page is the UI half of those decisions. The ops half is the staleness monitor and reconcile job (I-3) and the lag alert (I-33).
  2. The head clock replaces useBlockNumber, which is RPC, with useIndexerHead(chainId), built from _meta.status (I-10). Freshness is block age against a skew-corrected clock, not the ready flag. Production still runs Ponder 0.8, which reports ready; in 0.17 the _meta.status rows are {id, block} with no ready, and block can be null for a chain that hasn't started, which shows as Unavailable. The estimated head needs no RPC: indexed block + age ÷ slot time. Seat maturity, key expiry and gate eta countdowns all use this clock (I-13, I-26).
  3. The client is chain-aware: one indexer URL per chain (VITE_INDEXER_URLS), head parsing per chain key, and freshness gates keyed chainId:chamber, so the same address on two chains can't collide (I-10, I-5). Base and Arbitrum appear only as "not configured" rows. Spoke indexing waits for the Phase 2 gate (I-23, P-24), and a chain with no indexer shows Unavailable instead of polling RPC.
  4. The chip is on every page, in the top bar, next to the chain. It's the one place users learn where numbers come from. The details popover reports display RPC calls (always 0) and transaction RPC calls, the same numbers the CI RPC budget test asserts per route (I-21). "Refresh now" is a single indexer query.
  5. The four previews share one layout, so the only differences are the chip, the banner, the as-of labels and the buttons. The fresh-load case has nothing to show, so it gets an empty state with no actions. Healthy stays quiet; the block label is enough. Lagging warns but keeps actions on, because every write simulates at the latest block via RPC (#260) and that catches stale-state mistakes. Stalled pauses decisions that need current state and says why on each button. Freshness polling runs only while the tab is visible, replacing the Alchemy WebSocket and its 60 s invalidate-everything fallback (I-19). The stalled banner links the incident runbook (D-18), because the Chamber keeps working without the app.
  6. The rule for pausing: pause an action if a reasonable person could decide differently with current state, and keep it on if it only reduces authority or stops harm. That's why cancel votes, revoking a confirmation, clearing a session key and the guardian cancel export (M-16) stay available during an incident. Those are exactly when they matter.
  7. The freshness gate already exists (requireIndexerBlock, IndexerBehindError, 40 retries × 1.5 s in lib/indexer.ts). This design keys it by chain and Chamber (I-10), shows it in the chip, and defines the timeout copy. RPC appears only in the first three steps: simulate, send, receipt.
