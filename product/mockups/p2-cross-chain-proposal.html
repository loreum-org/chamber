Design notes

  1. Authority chain on every actor. The proposer, each confirmer, the director who sent it from Ethereum and the Base executor each show the signature element. All four are EOA owners, which can't set session keys, so the third node says "Owner" rather than disappearing. Submitting counts as the proposer's confirmation (WalletLib), which is why aria.eth appears in both places. Quorum is snapshotted at submit, and execute needs the higher of that and the live quorum (Chamber.sol M-04).
  2. One lifecycle, from the indexer. The six states (Proposed → Approved → Sent → Delivered → Queued → Executed) and the four exception states come from one table keyed by home chain, Chamber and wallet nonce (I-27, P-24). Delivered and Queued happen in the same Base transaction but are shown separately, because they fail differently. The app makes no Base RPC calls to draw this.
  3. Nested decode from bytes, never from prose. The tree follows the path messenger → receiver → Delay → Roles → Safe → USDC.transfer (P-14 chain-aware decoder, P-25 recursive decoder through receiveMessage). USDC amounts use 6 decimals from the token list; the current decoder hardcodes 18 (P-14 review note). The warning banner is the P-30 messenger-target flag. The messageId binds source chain, Chamber, nonce, destination and payload, per the review's replay fix.
  4. Honest timing. This replaces the v1.0 "15–30 s" promise with each real step and its actual duration: approval, about 2 minutes of delivery, and the 72 h delay. It points to bridge templates for speed, where solver capital, not message speed, makes the move fast.
  5. Preflight is the only RPC on this page. It runs only when the director asks (the preflight button, or Execute, which re-runs it right before the wallet opens), never on page load: an eth_call on Base from Delay into Roles for the inner call, plus queue-head and allowance checks (P-25 preflight, P-15, P-29 on-demand Base client). The panel shows the block and says it used RPC. The Execute button needs a write-only Base wallet client, because production wagmi has only mainnet and Sepolia (P-17/P-25 review notes).
  6. Guardian window, stated precisely. The 72 h cooldown is the guaranteed window. After eta the guardian can still cancel, but it races any executor. setTxNonce skips every lower entry (phase 2 open question 5), so the card lists what else would be skipped. The guarded-launch drill #58 (P-27) exercised this exact path on Sep 10, which is why #61 sits at Delay nonce 1. Exporting the cancel is destructive in intent, so it uses the ghost danger button and a typed phrase, like the M-16 guardian cancel export.
  7. Relayers are liveness only. This follows the P-8 naming: the relayer isn't an "operator" and holds no authority (P-26 asserts that its key has no Roles or Safe role). Auto-execute is off during the guarded launch (P-27), so a director executes by hand, which is why #61 is still waiting after eta.
