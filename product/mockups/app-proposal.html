Design notes

  1. Status in one sentence, lifecycle below it. The step row uses the same states the queue uses. "Indexed" is its own step: after a write, the page waits for the indexer to pass the receipt block (IndexerBehindError retries) instead of reading the chain (I-14, I-10).
  2. Timing risks come from other pages' state, shown where they bite. "Ready" is true now, but two indexed, scheduled events change it: the 5 → 6 seat change (timelock ends Mar 18 09:30, 2 of 3 supporters; SEAT_UPDATE_TIMELOCK is 7 days) raises quorum to 1 + ⌊6 × 51 / 100⌋ = 4, and the Grants Safe hands over to Loreum Grants at 15:00 (#262 parallel run). The banner gives the exact time and the consequence, and links to the page where each decision is made. The recipient check repeats the handover because a reviewer may land on the decode first.
  3. The decode is what executes. It comes from the calldata the indexer stored from SubmitTransaction, run through the #260 decoder (txDecoding.ts decodeTransactionAction). Every row shows the raw value next to its human form: amount in base units and USDC, full addresses with labels the indexer can back up (a past recipient, a director, a Chamber-owned Safe). The checks below it catch the classic mismatches: title vs calldata, unknown recipient, self-call, and cross-chain targets (P-30).
  4. The dataHash check is shown, not assumed. For external targets only keccak256(data) is on-chain (WalletLib), and executeTransaction reverts DataHashMismatch when the supplied bytes differ. The page hashes the indexer copy in the browser and compares it to the indexed dataHash. Execute re-reads the dataHash via RPC as a transaction-time preflight. This settles the M-16 risk about hash-only calldata without a getLogs display read.
  5. Simulation is a labelled, transaction-time RPC read. This extends #260 TxSimulationPanel in three ways: (a) it runs at the block the page is indexed at, so the balance diff agrees with the numbers on screen; (b) it shows the block and "via RPC"; (c) Execute re-runs it at head and shows both results if they differ. It never runs on page load (I-21).
  6. Each confirmation shows its authority chain, the signature element: seat → owner → signer (session key, policy account, Safe threshold or owner). Required confirmations are shown as max(submit snapshot, live quorum) (Chamber.sol _requiredConfirmations, audit finding M-04), with the pending seat change's effect next to it. Only live flags count: seat in the top set and the NFT owner unchanged since confirming (audit finding H-01, confirmOwner). The SUBMIT-includes-confirm behaviour is stated plainly (see the queue notes and C-17). Terminology follows P-9.
  7. Rationale is marked as a claim. Metadata can carry anything, including text written to mislead a reviewer or an AI director. It sits below the decode, is quoted, and is labelled unverified. The review calls for LLM drafting to write here, never into what gets signed.
  8. The high-risk self-call pattern (#48): a red banner says what the new code would control, in numbers. The decode shows newImplementation in full. Implementation checks come from the indexer (I-7 implementationSource) and the release pipeline (C-3, C-4 size gate). The audit line is an explicit placeholder and states that it covers v1.2.0 only. Confirm stays disabled until the simulation passes and the reviewer ticks the box. This is the per-Chamber quorum upgrade path that C-18 rehearses for incident response.
  9. Buttons say exactly what happens, and the preflight checklist says where each check comes from (indexer or RPC). "When you press Execute" spells out the only four moments this page touches RPC: preflight, sign, receipt, then back to the indexer. Revoke is a plain ghost button because it can be undone.
  10. Cancel uses the destructive pattern: a ghost danger button behind a typed confirmation. cancelTransaction records a vote that can't be withdrawn (there is no revoke for cancel votes) and cancels automatically at quorum. The copy says both. The typed phrase includes the proposal number so a reviewer can't cancel the wrong one from a stale tab.
