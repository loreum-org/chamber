Design notes

  1. Across first, behind a decision. The route order follows P-10 and the P-11 review note: Across first (native USDC, refunds on expiry, no retryable or fee math), with canonical routes only if approved. Whether any of this starts before the Phase 2 gate is P-31's call, so the ribbon says so. The template calls SpokePool.depositNow directly: Across's own SpokePool source marks ERC-7683 v1 as deprecated, and its quote buffer is 1 hour, so a plain deposit with a draft-time quoteTimestamp would revert after a normal approval period. depositNow stamps the quote time at execution (P-10 research).
  2. Min received is the real commitment. depositNow fixes outputAmount at submit, and speedUpDeposit needs a depositor signature the Chamber can't give (no ERC-1271, per the P-10 review note). The quote comes from the Across API only when the director drafts or clicks Refresh (P-12, acrossQuote.ts is user-triggered), and the page says plainly that it isn't signed. The fee-drift tradeoff is spelled out both ways.
  3. Fill deadline is relative to execution. The template uses fillDeadlineOffset, so time spent in approval doesn't eat the fill window. fillDeadlineBuffer is a per-deployment immutable, so the simulation reads it from the SpokePool instead of hardcoding it (P-10 correction a). That read happens only inside the user-triggered simulation, which keeps draft-time RPC at zero.
  4. Recipient is locked. This proposes an answer to phase 2 open question 2: an allowlist of only this board's registered spoke Safes, read from the indexer's spoke_config. "Move any asset anywhere" isn't a feature. Paying an outside party on Base is a separate spoke action with its own delay.
  5. Exact approve, deposit, revoke, all atomic. Each nonce is one call, so an ERC-20 bridge needs approve then deposit (P-13). executeBatchTransactions (Chamber.sol:797) makes the three legs atomic. The revoke leg protects against an upgradeable spender pulling less than approved (P-10 threat section). Metadata is director-written and untrusted, so the final leg commits to every leg's hash and the app verifies that commitment against indexer rows (P-13 review note). The UI states that the contract can't enforce bundle-only execution.
  6. Submission tradeoff. This shows n prompts through the deadline overload (P-28), which keeps the deadline and metadata. The alternative, one prompt through submitBatchTransactions, gives a 30-day default deadline and no metadata (phase 2 open question 3).
  7. Canonical bridge comparison, honestly. For Ethereum → Base the canonical route delivers in about 1–3 minutes. Its 7-day delay applies only to withdrawals back to Ethereum, which the table says doesn't apply here. The deciding difference is the token: the standard bridge gives bridged USDC, and a wrong L2 token bounces back as a 7-day withdrawal (P-10). No "seconds for everything" claim: Across is fast only because relayers front their own capital.
  8. Tracking without RPC. Status comes from the indexer's bridge_transfer table. It decodes FundsDeposited from the execute receipt, and a sidecar asks the Across status API only while a row is pending (P-16). The card refetches GraphQL only while a row is pending and the tab is visible (P-17), so idle spokes cost nothing.
  9. Simulation runs at transaction time only. It runs the bundle in order as the Chamber, plus destination checks through an on-demand Base client that is never registered as a wagmi chain (P-15, P-29). The panel names the block and says it used RPC. The fill itself can't be simulated, and the panel says that too. The #260 decoder is chain-aware and uses 6 decimals for USDC (P-14), and cross-chain targets get the P-30 warning.
