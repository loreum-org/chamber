Base

Base spoke · security 5

Receiving from home only
Verification
Native OP Stack messenger

The receiver accepts a call only from L2CrossDomainMessenger 0x4200…0007, and only when xDomainMessageSender() is Loreum DAO Chamber 0x3F1c…A92e on chain 1. No relayer, oracle or Loreum-held key can create a message.

Receiver rule
Sender, chain, nonce and validUntil are all checked

Rejects any other L1 sender (including other Chambers from the same Factory), a replayed home nonce, the wrong destination chain or Safe, and any message that arrives after its validUntil (the home proposal's deadline). The receiver is immutable: no owner, no proxy.

Execution delay
72 h cooldown · 7-day expiration

Every message waits 72 h in Zodiac Delay before anyone can execute it. An entry nobody executes within 7 days of its eta expires, so a stuck entry can't block the queue forever.

Guardian 6
Cancel only

Loreum Guardian Safe (3-of-5) holds one Roles permission: Delay.setTxNonce. It can skip queued entries. It can't queue entries, change the allowlist or move funds. Skipping moves the nonce forward, so it also cancels every entry queued before the target. Last drill: #58 cancelled Sep 10.

Permissions
Roles v2 allowlist · 6 target/selector pairs

Only the calls in the table below can run, with the parameter rules shown, inside a weekly allowance. Anything else reverts at execution.

Home dependency 7
Trusts the Chamber's address, not its code

A quorum upgrade of the home Chamber changes what can send to every spoke. The 72 h spoke delay still applies, and the watcher alerts on any Chamber upgrade proposal. Pausing the home Chamber doesn't stop messages already sent; only the guardian can.

Rollup
Inherits Base's own risks

Base's sequencer can delay delivery, within its forced-inclusion window for L1 deposits. Base's upgrade keys are outside Loreum's control. Loreum adds no bridge of its own.

Design notes

  1. Balances come from the indexer. Home balances come from the periodic vault and treasury snapshots (I-7, I-20). Spoke balances come from spoke-chain tables with a slower poll interval and their own RPC budget (P-24, P-29), because the review warned that Ponder's default one-second polling on every chain would bring back the Alchemy quota burn.
  2. Vault assets never move. The review: "Don't move vault assets to spokes" and "Counting spoke balances in the vault's totalAssets" is deferred. The banner says why in one sentence, so nobody proposes it by accident.
  3. Per-chain freshness. With three chains, one "Indexed 24 s ago" chip would hide a stalled spoke. The chip shows each chain's head age, and the side card shows head, age and poll interval. If one chain goes stale, only its numbers get marked (I-10 chain-aware client and head clock; I-11/I-21 zero display-time RPC). Ethereum keeps the app-wide 30-block warn threshold; spokes use a time threshold because their block times differ (Base 2 s, Arbitrum about 0.25 s).
  4. The authority chain, extended. The .auth element usually shows seat → owner → session key. For a spoke, the same element shows board → Chamber → verifier → receiver → Delay → Roles → Safe. The role list uses the P-8/P-9 names: "operator" still means a director's session key, and relayers, verifiers, guardians and watchers are separate roles.
  5. L2BEAT-style security panel. One row per trust question, with a green or amber bar and a rosette summary that has one slice per rated row (the receiver rule folds into verification), so the summary can't look safer than the rows. Data comes from the indexer's spoke_config (P-25). The parameters follow the P-19 spec defaults: 72 h cooldown and a 7-day expiration. Expiration must be above zero, because a failing head entry otherwise blocks the Delay queue forever.
  6. Guardian semantics are stated honestly. Delay.setTxNonce skips every entry below the new nonce, not just one (phase 2 open question 5). The panel says so, so nobody is surprised by a mass cancel.
  7. Home dependency is amber on purpose. From the P-19 review note: the spoke trusts the Chamber's address, not its code, so a quorum self-upgrade re-points every spoke. This is the one place the design inherits home-chain governance risk, so it isn't shown as green.
  8. Safe ownership is an open decision. This mockup shows module-only (no local signers), so only the home board can act. Break-glass local signers would bypass the board and would need their own row in this panel (phase 2 open question 4).
  9. Allowance meter counts queued entries. Roles checks allowances at execution, not at queueing. Two queued payments could each pass preflight and together overrun the allowance; the second would then fail and block the queue head until it expires. The meter shows queued amounts as reserved (hatched), and the composer counts them.
  10. Zero inbound messages. This is the hub-and-spoke rule from the review ("home accepts zero inbound messages"; "any authority flowing from a spoke back to home" is deferred). It gets its own card because it's the property that keeps a compromised spoke or bridge from reaching the board.
  11. What's not supported is listed. These come from the review's Cut and Defer lists: non-native routes wait for the Phase 3 multi-verifier Outbox, and there are no mirrored boards, bridged seats or cLORE, and no Superchain interop. The page doesn't promise speed; it shows delivery time plus the 72 h delay.
  12. Activity from the indexer. Bridge rows come from bridge_transfer (P-16) and messenger rows from the cross-chain lifecycle table keyed by home chain, Chamber and wallet nonce (I-27, P-24). Fill time is measured from execution so it isn't mistaken for end-to-end governance time. #58 is a scheduled guardian-cancel drill from the guarded launch (P-27); it proves the cancel path on real infrastructure and is why #61 sits at Delay nonce 1.
