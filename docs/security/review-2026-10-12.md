**Method:** `.claude/skills/solidity-security-review`. Slither 0.11.6, Aderyn 0.6.8 and Halmos 0.3.3

## Fixed findings

### [R-1012-H1] Chamber-held or burned seat NFTs lower quorum; one incumbent can drain the vault
**Severity:** High. **Location:** `BoardLib.countReachableAuthorized`, `Chamber.getQuorum`,
`_requiredConfirmations`, `recoverSeats`, `delegate`.

PMN-M01 made quorum `quorumFor(n)` where `n` excluded top-seat tokenIds that are burned or owned by
the chamber. Rank still came from delegated weight, and `delegate` accepted chamber-held tokenIds.
Anyone can send an NFT to the chamber. An incumbent director (whose `seatedAt` is not reset while
they stay in the top set) could, in one transaction with flash-borrowed vault asset, delegate to
chamber-held tokenIds so they outrank the honest directors. `n` dropped to 1, quorum became 1, and
the attacker could submit (auto-confirm) and execute a transfer of the whole vault. The same state
made `recoverSeats(myToken, 1)` available with no timelock. Burnable collections allowed the same
by burning weighted tokens.

**Proof:** `Finding_R1012_ChamberHeldSeatSink.t.sol` (quorum fell from 2 to 1 on `7e52bb8`).

**Fix:**
- Quorum denominator is now occupied top seats, `min(seats, size)`. Burned or chamber-held ids count
  until removed, so a same-block rank change cannot lower quorum.
- `cleanupInertSeat` also removes chamber-held nodes (they can never act as directors), which keeps
  the PMN-M01 liveness property: anyone can drop an inert seat in one call.
- `delegate` reverts for chamber-held tokenIds.

Trade-off: between an NFT becoming inert and someone calling `cleanupInertSeat`, quorum is higher
than the number of directors who can vote. The call is permissionless.

### [R-1012-M1] Stranded delegations subtracted from a re-inserted node
**Severity:** Medium. **Location:** `Chamber.undelegate`, `BoardLib.insert` / `remove`.

Eviction removes a node but keeps each holder's `holderDelegation` (Finding 11). If the tokenId was
later re-inserted, `undelegate` subtracted the stranded amount from the new node, which only held
weight delegated after re-insertion. Effects: board weight below the holders' sum, later delegators'
full `undelegate` (and so `redeem`) reverting with `AmountExceedsDelegation`, and a cheap way to
erase other people's weight on a token (build stranded weight by delegate / evict / free the slot).

**Proof:** `Finding_R1012_StaleEvictedSubtraction.t.sol`.

**Fix:** `BoardStorage.nodeEpoch` increments whenever a node is removed. Chamber tracks each
holder's `liveDelegation` for the current epoch (`holderEpoch`). `undelegate` only takes live
weight off the board; stranded weight leaves `holderDelegation` without touching the node. Holders
from before an upgrade (`holderEpoch == 0`) fall back to the old behaviour, capped by the node so it
cannot revert. All three new mappings are appended to their ERC-7201 structs.

### [R-1012-M2] SUBMIT-only session key votes by submitting
**Severity:** Medium. **Location:** `Chamber._sessionScopeForSelector`, `WalletLib.submitTransaction`.

Every submit auto-confirms for the submitting token, but the session check for submit selectors
required only the SUBMIT bit and no delay. A "propose-only" key cast a counted vote on everything it
submitted, including in the block the key was set.

**Proof:** `Finding_R1012_SessionSubmitConfirms.t.sol`.

**Fix:** submit still needs only SUBMIT and is not delayed, so propose-only keys keep working.
The submit only records the submitting token's confirmation when the caller is the NFT owner, or a
session key that could confirm right now (CONFIRM scope and past `liveAt`). A propose-only key, or
any key before `liveAt`, submits without a vote. Scope checks now require all mapped bits.
`ChamberAuthHarness` mirrors the change.

### [R-1012-M3] Wallet transactions can spend third-party approvals
**Severity:** Medium. **Location:** `Chamber._validateTransaction`, `submitBatchTransactions`.

Depositors approve the chamber on the asset, often without limit. Only self-calls were restricted,
so a quorum transaction calling `asset.transferFrom(depositor, x, amount)` could take funds the
depositor never deposited, beyond the documented trust model (PMN-I02 covers chamber-held assets).

**Proof:** `Finding_R1012_ApprovalPull.t.sol`.

**Fix:** calls to the vault asset may only be `transfer` or `approve` (or carry empty data).
The first version of this fix used a selector denylist, which DAI `move` / `pull` and ERC-1363
`transferFromAndCall` bypassed (`Finding_R1012_ApprovalPullAliases.t.sol`). For other targets,
`transferFrom`, ERC-721/1155 `safeTransferFrom`, `safeBatchTransferFrom`, `burnFrom`, DAI `move` /
`pull`, ERC-1363 `transferFromAndCall` and ERC-777 `operatorSend` must name the chamber as `from`
(single and batch submit). Trade-off: a WETH-asset chamber cannot call `withdraw` on the asset to
unwrap; it can transfer WETH elsewhere to do so. Transactions submitted before an upgrade are not
re-checked at execute.

### [R-1012-M4] Seat updates use only the proposal-time quorum
**Severity:** Medium. **Location:** `BoardLib.executeSeatsUpdate`.

Wallet execution requires `max(submitQuorum, liveQuorum)` (M-04); seat updates did not. A lone early
director could propose with quorum 1 and execute after 7 days over a board that had grown to need 3,
and later directors cannot cancel before day 14.

**Proof:** `Finding_R1012_SeatUpdateLiveQuorum.t.sol`.

**Fix:** `executeSeatsUpdate` requires `max(proposal.requiredQuorum, getQuorum())`.

## Open findings

### [R-1012-M5] Seat-update support is not bound to the controller
`proposal.supporters` stores bare tokenIds. `executeSeatsUpdate` counts a supporter that is still in
the top set and has any owner, so support survives a sale or a short rental, and nobody can withdraw
it. Wallet votes record `confirmOwner` (PMN-H01) for exactly this reason.
**Recommendation:** store the supporter's `ownerOf`, skip mismatches like
`flagBelongsToCurrentController`, and add a withdraw-support path.

### [R-1012-L1] `maxWithdraw` / `maxRedeem` ignore the delegation lock
`redeem(maxRedeem(u))` reverts for any holder with delegations. **Recommendation:** return
`min(super, balance - totalHolderDelegations)` and the matching asset value.

### [R-1012-L2] Wallet treats `false` returns as success
`WalletLib.executeTransaction` checks only that the call did not revert. A token that returns
`false` consumes the nonce with no transfer. **Recommendation:** if return data is 32 bytes and
decodes to `false`, revert `TransactionFailed`.

### [R-1012-L3] Phantom functions through `fallback`
The payable catch-all `fallback` succeeds for any selector, including `permit`, so routers that
call `permit` then `transferFrom` proceed silently. **Recommendation:** keep `receive` and revert in
`fallback` (or only accept calls with value).

### [R-1012-L4] Owner-bound state revives on round trip or re-mint
A `DirectorSession` comes back live (old scope, expiry and an already-passed `liveAt`) if the NFT
leaves and returns to the same contract owner. A sync while a top-seat token is burned deletes
`seatedOwner` but keeps `seatedAt`, so a re-minted id gets a mature seat. **Recommendation:** clear
the session on any observed owner change, and reset `seatedAt` when binding a new owner.

### [R-1012-L5] UNSCOPED keys reach unmapped functions without delay
`recoverSeats` has no entry in `_sessionScopeForSelector`, so an UNSCOPED key calls it the block it
was set, and any future director function is granted to existing UNSCOPED keys automatically.
**Recommendation:** map `recoverSeats` (delayed), and make unmapped selectors delayed.

### [R-1012-L6] Upgrade path has no compatibility check
The chamber owns its ProxyAdmin, so only the current implementation can upgrade. Neither
`upgradeImplementation` nor `_validateTransaction` stops a quorum from upgrading to a contract
without the wallet, or calling `ProxyAdmin.renounceOwnership` / `transferOwnership` directly.
Either locks all assets or removes upgrade control. **Recommendation:** a Chamber-only UUID probe in
`upgradeImplementation`, and reject or restrict `target == getProxyAdmin()`.
**Update (1.3.0):** `upgradeImplementation` was removed; a quorum transaction to the ProxyAdmin is now the only upgrade path. ProxyAdmin is the single upgrade path and has no version or migration checks of its own; the board is responsible for what it approves. The compatibility check and the ownership-call restriction remain open.

### [R-1012-L7] Chamber exceeds the EIP-170 size limit
A local build with the repo's `foundry.toml` (solc 0.8.30, via-IR, 200 runs) gives Chamber
26,446 bytes of runtime code on `7e52bb8`, 1,870 over the 24,576 limit. Foundry tests do not
enforce the limit, so nothing fails. If the deploy uses the same settings, `new Chamber()` reverts.
This branch moves the new logic into `BoardLib` / `WalletLib`, but still adds 542 bytes (26,988).
**Recommendation:** confirm with `forge build --sizes` against the deploy profile; if over, move
more Wallet/Board paths into the external libraries or lower `optimizer_runs` for Chamber.

### Info
- ERC-7201 `@custom:storage-location erc7201:loreum.X` annotations do not match the constants, which
  hash `"erc7201:loreum.X"`. Storage is fine; layout tooling is misled. Fix the annotations, not the
  constants.
- Upgrade `data` runs as the ProxyAdmin while the reentrancy guard is held, so `nonReentrant` or
  `msg.sender == address(this)` migrations revert. Document `reinitializer` migrations.
- Factory's `VERSION()` probe accepts an existing Chamber proxy as the implementation.
- `createChamber` cannot pin the implementation; the owner can swap it before a pending create.
- Zero-value and self transfers of shares revert, against ERC-20 expectations.
- tokenId 0 can never be delegated (list sentinel).
- Clearing a compromised session key leaves its votes in force; cancel votes cannot be withdrawn.
- Correction to the skill baseline: `executeSeatsUpdate` calls `refreshSeating` once, not twice.
